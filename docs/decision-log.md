# 决策日志（decision log）

这份文档专门记录：

> **为什么这个仓库、这条研究链、这套维护方式，要这样定。**

很多东西如果不记下来，过几天就会只剩“结果”，忘了“为什么当时要这么做”。

---

## 1. 使用方式

以后如果你遇到下面这些情况，建议往这里追加一条决策记录：

- 仓库结构被重新组织
- release 策略改变
- 研究主线发生明显转向
- 某条构建流程被正式固定
- 某类二进制被明确禁止/允许进入 release

建议格式：

```md
## D-00X <标题>

- 日期：
- 状态：Accepted / Superseded / Deprecated
- 结论：
- 原因：
- 影响：
- 如果未来要推翻，需要满足什么条件：
```

## 2. 当前已记录决策

## D-001 仓库定位为 source-only / doc-first 私有研究快照

- 日期：2026-06-30
- 状态：Accepted
- 结论：
  - 这个 GitHub 私有仓库不追求成为完整运行环境镜像，而是优先保存源码、脚本、去敏文档和阶段总结。
- 原因：
  - 本地原始环境里包含较多运行时目录、报告树、落地材料和环境耦合信息，不适合直接整体导出。
- 影响：
  - 仓库更适合归档、回溯、整理，而不是直接拿来还原完整实验环境。
- 如果未来要推翻，需要满足什么条件：
  - 必须先重新设计一个专门用于复现实验的去敏分发结构。

---

## D-002 原始 reports 与运行时目录不直接入仓库

- 日期：2026-06-30
- 状态：Accepted
- 结论：
  - 不把原始 `reports/`、`dist/`、Windows 落地文件直接纳入当前 GitHub 私有仓库。
- 原因：
  - 这些内容通常包含：
    - 本地绝对路径
    - 环境拓扑
    - 原始实验材料
    - 运行时强绑定文件
- 影响：
  - 仓库中保留的是“索引与说明”，原始证据继续本地保存。
- 如果未来要推翻，需要满足什么条件：
  - 必须先完成更细粒度的去敏和分层归档。

---

## D-003 Release 默认只走 docs-first，不默认挂运行型二进制

- 日期：2026-06-30
- 状态：Accepted
- 结论：
  - GitHub release 默认优先挂：
    - 文档包
    - 源码 tag
    - 去敏摘要
  - 默认不挂：
    - `*.exe`
    - `*.dll`
    - `*.bin`
    - `*.dat`
    - 容器 meta / build log
- 原因：
  - 可执行样本、payload/container、meta/log 往往仍然会暴露明显运行材料或结构细节。
- 影响：
  - 这个仓库的 release 更像研究归档，不像运行材料分发点。
- 如果未来要推翻，需要满足什么条件：
  - 需要先完成一轮专门的二进制资产审计，并形成新的 allowlist。

## D-004 仓库长期维护依赖治理文档，而不依赖聊天上下文

- 日期：2026-06-30
- 状态：Accepted
- 结论：
  - 以后尽量把关键说明固化在仓库文档里，而不是只保留在临时对话中。
- 原因：
  - 对话上下文会散、会丢、会很难回看。
- 影响：
  - 增加了 `CHANGELOG.md`、`repo-map`、`build-matrix`、`binary-release-policy` 等治理文档。
- 如果未来要推翻，需要满足什么条件：
  - 没有必要推翻；只需要继续补充和更新。

## D-005 “改源码 != 新样本生效”被固定为显式规则

- 日期：2026-06-30
- 状态：Accepted
- 结论：
  - 以后默认把“源码改动”和“构建/同步/重启/重新生成/重新下发”分开看。
- 原因：
  - 之前这类问题反复出现，是最典型的实验混淆来源之一。
- 影响：
  - 后续优先使用 `docs/build-matrix.md` 来判断每轮实验需要哪些动作。
- 如果未来要推翻，需要满足什么条件：
  - 除非后面完全重构成一键且可验证的统一流水线，否则不建议推翻。

## D-006 loader/container 研究与 direct_https 运行链要同时记录，但分层理解

- 日期：2026-06-30
- 状态：Accepted
- 结论：
  - 后续研究中要明确区分：
    - direct_https agent 本体问题
    - loader 问题
    - container/packer 问题
- 原因：

- 影响：
  - 以后每轮实验都建议写清“改动层级”。
- 如果未来要推翻，需要满足什么条件：
  - 没有必要推翻，只需要继续细化。

- 日期：2026-07-01

- 如果未来要推翻，需要满足什么条件：
  - 只有在你形成了更适合自己的固定模板时，才考虑替换。

## D-008 WPP/WPS 功能候选与源码快照分层保存

- 日期：2026-07-23
- 状态：Accepted
- 结论：
  - WPP/WPS 宿主代理、profile-only loader、direct_https agent 源码和阶段说明进入私有研究仓库。
  - 最终 `dll/dat/bin/so`、原始扫描日志和环境绑定快照继续由本地候选目录保存，仓库记录其哈希和验证摘要。
- 原因：
  - 源码需要长期回溯，运行材料需要按具体靶机和构建环境管理；两者混在一起会让版本边界和复现条件变得模糊。
- 影响：
  - 仓库保持 source-only / doc-first，同时拥有完整的 WPP/WPS 调用链说明、三次部署结果和主要文件指纹。
- 如果未来要推翻，需要满足什么条件：
  - 先完成单独的二进制资产审计、去敏检查和新的 allowlist，再调整 release 策略。

## 3. 如何继续维护

- `D-008`

如果旧决定被新决定替代，就把旧的状态改成：

- `Superseded`
